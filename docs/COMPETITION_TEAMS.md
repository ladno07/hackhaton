# Команды в рамках соревнования

## Сценарий

1. Федерация создаёт соревнование с `entry_mode=team`, задаёт `team_min`/`team_max` (1–50, минимум не больше максимума) и `team_rating`. Эти настройки меняются только в черновике.
2. Спортсмен создаёт команду и становится капитаном с подтверждённым собственным участием. Тренер создаёт команду из своих действующих подопечных по дисциплине соревнования и приглашает капитана; согласие капитана не подразумевается.
3. Капитан или создавший команду тренер приглашает участников по публичному ID вида `FSP-000123`, который спортсмен копирует в «Моём профиле». Перед отправкой показывается карточка: ФИО, ID, организация и муниципалитет. Поиск по ФИО остаётся вспомогательным и показывает те же данные для различения однофамильцев. Тренер выбирает из полного списка своих действующих подопечных по дисциплине соревнования. Спортсмен подтверждает или отклоняет приглашение в соревновании → «Команды». Уведомление содержит ссылку на эту вкладку.
4. После всех подтверждений капитан или тренер подаёт общую заявку. Сервер проверяет размер состава, подтверждения, наличие капитана, возрастные группы, действующую дисциплину и отсутствие отстранения у каждого участника. При подаче тренером также проверяется связь со всеми участниками.
5. Федерация повторно проверяет допуск и принимает заявку целиком либо возвращает с причиной (не менее пяти символов). При допуске создаётся проекция состава в `competition_applications`, совместимая с существующими протоколами и отчётами. Отдельные заявки в командном зачёте подавать или модерировать нельзя.
6. В статусах «На рассмотрении» и «Допущена» состав заморожен. Пока приём открыт и срок не истёк, капитан, создавший тренер или федерация могут вернуть заявку на редактирование с основанием. Допуск снимается у всего состава; после замены участника и нового согласия необходима повторная подача и одобрение. После закрытия приёма замены недоступны.
7. После завершения соревнования и закрытия приёма федерация вводит один результат на каждую допущенную команду. Сервер разворачивает его на подтверждённых участников; место и баллы едины. Места считаются по командам: две команды могут занять 1-е и 2-е места независимо от размера состава. Одинаковые места — по правилу «1, 1, 3».
8. Публикация и исправление результата используют существующий механизм редакций протокола, выгрузок и уведомлений. Состав опубликованной команды менять нельзя.

## Согласия и ограничения

- Подтвердить участие может только сам спортсмен. Подтверждённое участие в двух командах одного соревнования запрещено API и частичным уникальным индексом БД. Получать несколько приглашений разрешено.
- До допуска команда видна её участникам, создавшему тренеру и федерации. Допущенные команды видны пользователям соревнования.
- Участник может отозвать согласие до допуска; заявка на рассмотрении при этом возвращается на исправление. Подтвердивший капитан сначала передаёт капитанство. Назначенный тренером капитан может отклонить неподтверждённое приглашение.
- Команду в черновике или на исправлении можно снять с соревнования с причиной; подтверждения освобождаются, история остаётся в журнале. Для снятия допущенной команды сначала снимается допуск.
- Название уникально в соревновании без учёта регистра. Капитан меняется только на участника текущего состава; для подачи он должен подтвердить участие.
- Личный рейтинг за командное место начисляется каждому участнику только при `team_rating=true`. Баллы выступления и рейтинговые очки — разные величины. История выступлений и сводка тренера отображают результат независимо от этой настройки.
- Постоянные клубные команды, запасные и переходы между соревнованиями не реализованы.

## Совместимость и запуск

Миграция `0007` добавляет `competition_teams`, `competition_team_members` и настройки зачёта в `competitions`. Старые соревнования сохраняют личный режим; прежние строки и версии протоколов, включая введённые ранее названия команд, не переписываются. Автоматически выдавать согласия участникам старых протоколов нельзя. Для нового сценария создайте новое соревнование с командным зачётом.

В папке проекта: `docker compose up --build -d backend frontend`. Backend применяет миграции при запуске. Удалять том PostgreSQL или повторно загружать демоданные не требуется.

## API

Все пути начинаются с `/api/competitions/{comp_id}`.

| Метод и путь | Действие |
| --- | --- |
| GET `/teams` | Видимые команды и составы |
| GET `/team-candidates?public_id=FSP-000123` | Точное совпадение публичного ID |
| GET `/team-candidates?q=...` | Дополнительный поиск по ФИО, от двух символов |
| GET `/team-candidates?mine=true` | Все активные подопечные тренера по дисциплине соревнования |
| POST `/teams` | Создание: `name`, `captain_id` |
| PUT `/teams/{id}` | Название и капитан |
| POST `/teams/{id}/members` | Приглашение: `public_id` (совместимый `athlete_id` также поддерживается; указывается только один идентификатор) |
| PATCH `/teams/{id}/response` | Собственный ответ: `accepted` / `declined` |
| DELETE `/teams/{id}/members/{athlete_id}` | Исключение до допуска |
| POST `/teams/{id}/submit` | Подача общей заявки |
| PATCH `/teams/{id}/review` | Федерация: `approved` / `returned`, `comment` |
| POST `/teams/{id}/reopen` | Отзыв заявки / снятие допуска: `reason` |
| POST `/teams/{id}/cancel` | Снятие команды: `reason` |
| POST / PUT `/results` | Публикация / исправление: `team_results: [{team_id, place, score}]`; для исправления дополнительно `reason` |

## Проверки

Добавлены 10 API-тестов и тест миграции: полный цикл, личный рейтинг включён/выключен, протокол и выгрузка, исправление результата, подтверждение и отзыв согласия, запрет участия в двух командах, возврат и замена состава, повторный допуск, возраст/дисциплина/отстранение, права тренера и капитана, размер состава и сроки, поиск по кириллице, две команды и защита от пропущенных/повторных результатов. Проверка миграции выполняет upgrade/downgrade на изолированной БД и сверяет схему с моделями.

Команда: `python -m pytest tests/test_competition_teams.py tests/test_team_migration.py -q`. Полный набор: `python -m pytest tests -q`. Автоматические API-тесты выполнялись на SQLite в памяти; SQL миграций PostgreSQL дополнительно скомпилирован offline. Проверка миграции на живом PostgreSQL из среды чата не выполнялась.

## Публичный ID спортсмена

ID вида `FSP-000123` однозначно соответствует постоянной записи спортсмена, не зависит от ФИО, муниципалитета или организации и доступен существующим аккаунтам. Он отображается в профиле, реестре, составе команды и списке подопечных. Это публичный идентификатор карточки, а не пароль, токен авторизации или реализация OpenID Connect. Дополнительной миграции для него не требуется: номер формируется из существующего неизменяемого первичного ключа спортсмена. По ID не раскрываются дата рождения, контакты, согласия и медицинские сведения.

При вводе нового ID или смене способа поиска выбранный получатель сбрасывается. Отправка недоступна до загрузки карточки; после поиска по ФИО требуется явно выбрать получателя. Добавлены тесты на одинаковые ФИО, адресную доставку приглашения, стабильность ID после переименования, границы доступа тренера и некорректные ID.
